# 三套 AI 团队：从零到验收的真实模型实测

此文保留投研 1.0.x、内容 1.0.0 的历史实测，不代表后续版本已通过。新版见 [开源团队适配与试跑](开源团队适配与试跑.md)。

日期：2026-11-27（北京时间）。这是 [首轮团队包验收](团队包验收.md) 的后续全量试跑，测试记录保留首轮失败与修改经过，不以最后一次成功覆盖失败证据。

结论：三套团队从新建项目跑到完成，17/17 个角色、22/22 个角色 Skill 均有真实成功记录。调用与流程通过本轮功能验收；交付质量经过打回改善，但仍有两项来源/审阅身份标注问题，见下文。不能据此宣称免人工审核或任意任务都能一次成功。

## 范围与判定方法

使用现有本机模型配置和真实 Claude Agent SDK，新建独立项目，通过真实工作台 HTTP 接口提交需求、回答澄清、确认、打回、停下和重试。没有用替身 Agent 生成交付物，也没有手工修改 Agent 产物或项目状态来取得通过。

三个团队合计声明 17 个角色、22 个角色 Skill。角色执行以 SDK 返回结果为证；Skill 以 SDK 会话中的 `tool_use` 与成功 `tool_result` 配对为证，不能只凭进度里出现“调用 Skill”算成功。三个包的协作 Skill 作为系统指令注入，另外核对依赖、交接、并行、确认和恢复行为，不把它们计作三次独立工具调用。

本轮关口由 Codex 作为用户授权的测试操作者审阅后调用正式接口提交，**不是多位真人的验收记录**。语义质量评审是实施 Agent 的诊断性评审；确定性浏览器断言、文件检查与模型自述分开记录。合成需求、访谈和业务参数均标明为测试材料。

### 网页效果

活动为 2026 年 12 月 6 日 14:00–16:30、晴岚书屋、《小王子》，3 个名额。页面说明是本机演示，无后端。姓名必填、手机号为 1 开头的 11 位数字、重复手机号不新增，第 3 人成功反馈保留姓名和剩余 0 人，随后不能再报名；浏览器存储不可用时退回内存并告知刷新会丢失。

真实链路覆盖包内全部 12 个节点：澄清、问题表单、PRD 确认及打回、设计及打回、开发、走查、验收及打回开发、再次走查、完成。最终交付包含 9 条功能需求、7 条成功标准和 5 个可直达状态。

Chrome 实际提交表单、刷新页面、切换状态和模拟存储拒绝。22 项断言覆盖字段校验、重复提交、三次成功与满额、成功后清空、刷新持久化、5 个 hash 状态、状态演示不污染真实数据、未知状态回退、390px 无横向溢出、存储降级及浏览器异常。实施 Agent 另行查看了桌面与手机截图。

第一次自动走查自报 16/16，但独立浏览器验收发现第 3 人成功后表单未清空，实际为 21/22。通过正式打回开发入口修复后，再次走查记录 `round: 2` 和上一轮结果，浏览器达到 22/22。这证明“文件检查通过”和“模型走查通过”不能替代实际交互验收。

### 投研效果与复核口径

唯一公开来源为 [Newtype 固定提交 README](https://raw.githubusercontent.com/newtype-01/newtype-codex/e22b7771549572439a092295bb370075ded261a3/README.md)，通过真实公开 URL 读取工具取回，没有搜索其他资料。

合成参数：每周 30 篇、每月 4 周；原流程每篇 90 分钟，假设新流程制作 60 分钟加人工复核 15 分钟；首月学习 8 小时、人工每小时 200 元、API 每月 300 元。复核答案为原工时 180 小时、新工时 150 小时、节省 30 小时；按假设计价稳态 5,700 元、首月 4,100 元，均不是实测收益或现金节约。

月度公式为 `P稳 = 400 × (90 − t) − C`，首月再减 `200L`；在 `C=300、L=8` 的假设下，临界耗时为 89.25 和 85.25 分钟。75 分钟距两条临界线分别为 14.25 和 10.25 分钟。质量不劣于旧流程的等号可计入满足；经济盈余要求严格大于零，等号归入停止，不得交叉矛盾。

雷达、分析师、创投评审、判断师、建议师和研究主理人均实际执行；分析师与创投评审存在真实并行。版本 1.0.1 加入证据分类、不得编造数字置信度、采用与停止条件一致等规则；初稿仍出现算术、来源标签和推断越界，验收时逐项打回，而不是把“已生成报告”当成质量通过。

修订后的最终报告已纠正关键算式、作者人数推断、免费与退出成本推断、安装细节标签及样本口径。保留问题：来源附录只汇总了首轮读取时间，遗漏雷达本轮 18:39（北京时间）等新抓取记录；实际工具证据中有这些读取，来源固定提交未变。该附录不能充当完整的取证审计日志。

### 内容团队效果与复核口径

输入为项目内的合成访谈、已有知识简报及同一份固定 README。副主编规划了知识盘点、提取、研究、初次核查、写作、编辑、交付前核查和主编汇总。八个角色均实际执行，不用主编代替专业角色。

核查实际识别了“八个角色提高十倍产能”没有数据，以及“继承模型就是自动共享全部项目记忆”的混淆。交付前核查也发现稿件把一次安装授权误写成每个角色逐个授权。独立验收进一步要求区分“安装八份可选角色模板”与“按任务派工”，在正文首次使用访谈时注明合成示例，不能把 AI 自查说成真人审阅。

打回后副主编只选择编辑、终稿核查、汇总三项，没有重做研究与提取。最终正文不含主标题为 994 个非空白字符（其中汉字 840），附录另列；确认后资料管理员再次实际调用 Skill，将结论、来源和项目经验写入 `.newtype/knowledge/accepted.md`，项目进入完成。

保留问题：归档把平台的确认动作推成了“真人验收”，而本轮实际由 Codex 代理提交。**该句话不是事实，不能据此记为真人已审阅**。正文已说明 AI 核查、尚待真人验收；归档身份仍应以测试操作日志和平台事件为准。本轮没有手工改归档文件掩盖这项问题。

## 实测中修复的问题

| 发现 | 处理与证据 |
| --- | --- |
| 线框把状态写成 `{id,name}` 对象数组 | 原契约拦住；原角色重试修正。校验错误现在明确要求字符串数组，补回归测试 |
| 同角色续用会话时，重试只改文件而没再调用必需 Skill | 原守卫拦住，没有降低要求；派活明确每轮须实际重新调用。新增“有产物但没 Skill 仍失败，实际调用后重试通过”测试 |
| 1280px 线框加 padding 导致横向溢出 | 经正式设计打回修复，1280px 与 390px 复测无溢出 |
| 自动走查漏掉末位报名后清空表单 | 独立浏览器发现，打回开发并自动再次走查；22 项实际浏览器检查通过 |
| 投研自报置信度、把未知推成事实、停止条件矛盾 | 观澜包发布本机 1.0.1，旧项目锁定旧包；相同输入另建项目重测，保留失败原文与关口意见 |
| 主动结束的失败项目显示成“已完成” | 结束项目单独显示“已结束”，收尾卡明确文件保留，补充状态与卡片测试 |
| 重试已经执行，界面仍保留失败操作 | 将上次错误保留为重试上下文，当前状态恢复执行中并提供“停下”；新增失败、重试、停下的整条回归 |

未更改原有网页阶段表，也未修改已经开工项目锁定的包文件。更新包只对新选择该版本的项目生效。

## 并发、隔离和恢复

- 三个测试项目同时推进，共用主服务的全局名额，观测峰值为 3，不是每个团队各 3。
- 角色 SDK 配置和会话按项目真实路径与角色分开；成功会话号未跨“项目＋角色”复用。三个项目的独有代号未在其他项目交付文件中出现。这是本组样本证据，不是所有输入下绝不串话的证明。
- 暂停并重启测试服务后，投研保留 5 个已完成专业任务，只恢复主理人汇总；内容保留前 6 项，从终稿核查继续。没有重做已完成节点。
- 工作流授权拒绝根目录泛查和越界路径时，Agent 改用已授权的具体目录；拒绝记录与最终成功记录均保留，不把所有工具尝试描述为成功。

## 工程检查和复现

`npm test`：226/226；`npm run smoke`：92 个模块语法检查、替身工作台和干净目录 setup 均通过。观澜 1.0.1 还通过结构校验和导出后干净目录重新导入，摘要一致。工程检查与上面的真实模型试跑分开计数。

复现时先按 [团队包安装提示词](prompts/ecosystem.md) 配好本机模型并安装三个包，在 `/teams` 选择团队新建项目，使用本页相同输入。网页先要求澄清；内容明确要求全部八角色，否则按需规划合法地只选择部分角色。投研只给固定 README 和上述假设；检验来源与算式，不把“文件存在”当成内容正确。

内容案例的具体素材可写入该项目的 `inputs/interview.md`：

```text
# 墨潮访谈素材（合成测试材料）
林编辑：我主张先明确交付和交接，再按任务选择角色。
周作者：我听说只要配置八个角色就能提高十倍产能，而且模型会自动共享全部项目记忆；这些说法我没有数据。
林编辑：研究来源与作者观点要分开，最终稿应该有人检查。
```

已有知识简报写入该项目 `.newtype/knowledge/brief.md`：读者是第一次接触 AI 团队的内容负责人；口吻直接、具体、少术语；简报是测试材料，不是公开研究结论。需求指定正文 800–1000 字，附来源、事实与观点区分及缺口；副主编计划包括 `lookup、extract、research、verify、draft、edit、final-check、synthesis`，验收后归档。只把素材放进目标测试项目，不覆盖其他项目资料。

每个关口保存当前产物、状态和意见，再通过工作台确认或打回。发生错误时先保留失败记录，修复后重试本步；包规则修改要升版本、新建回归项目，不能热改旧项目的包锁。最终列出角色成功调用、Skill 成功工具结果、工作流节点、实际交互与语义复核结果。

原始用例、SDK 事件、全部关口快照、浏览器断言、截图和失败记录保存在实施机器 `本地资料/2026-11-27-三团队全量实测/`，包含运行路径与项目数据，不随仓库提交。

收尾已重启本机主服务加载运行修复，工作台正常，原有两个已完成网页项目仍为完成状态；观澜 1.0.1 已安装，旧版本保留供既有项目使用。本轮代码与文档改动保留在本地工作区，未提交或推送 GitHub。

## 本轮未验证的范围

本轮完整流程在本机工作台执行，没有新建飞书机器人，也没有把投研、内容团队用齐全部机器人和多位真人跑一遍群内流程。公开 URL 读取已实测，Brave 搜索、PDF/音视频提取、本轮真人分工验证和服务器部署未覆盖。没有进行独立 Grok 审查；上述质量复核与失败路径审查由实施 Agent 完成。
