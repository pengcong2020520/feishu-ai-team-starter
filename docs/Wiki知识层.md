# Wiki 知识层

团队包可以带业务知识。运行中形成的项目决定、协作约定和原始对话分别保存，Agent 按问题检索，无须把全部资料塞进每次提示词。

| 层次 | 保存什么 | 谁能读取 | 如何更新 |
| --- | --- | --- | --- |
| 团队知识 `team` | 业务术语、产品事实、方法、可分享案例 | 锁定这个版本的项目角色 | 管理员复制团队草稿、修改 Wiki、试跑后应用新版本 |
| 项目知识 `project` | 本项目需求、决定、依据和交付约定 | 本项目的角色与管理员 | 管理员私聊指定项目编号更新 |
| 协作记忆 `collaboration` | 偏好、协作约定、待办、待核实观点 | 指定项目时仅限本项目；未指定时仅限管理员本人 | 管理员私聊维护；工作中的角色可保存本项目待确认笔记 |

团队知识随包分享。项目知识和协作记忆保存在 `data/knowledge/`，不自动进入团队包。文枢已有的 `.newtype/knowledge` 继续遵守原 Skill，不自动搬进公共 Wiki。

## 开始使用

先按已选版本完成标准 setup 和管理员连接。已有安装更新代码并重启原服务，保留数据、工作区和 SDK 会话目录；没有额外的 Wiki 开关。完整复制指令与检查顺序见 [Wiki 搭建提示词](prompts/knowledge.md)。

## 在飞书中使用

私聊「AI 管理员助手」，直接说：

> 从文枢复制个人草稿“门店内容团队”，加入团队知识：读者是小店经营者，文章不超过900字。来源是我这条要求。先试跑，不应用。

> 把项目 #实际编号 的交付约定存入项目知识：周四16:30交稿；来源是今天的排期讨论。保留旧版。

> 记住我的回复偏好：先说结论，简单问题简短回答。这是个人偏好，不放进公开团队包。

> 查一下刚才的字数约定，当前是什么，之前是什么，依据是哪条消息？

管理员通过 `wiki_lookup` 查找、分段读取和查旧版；`wiki_update` 修改当前页。正文、摘要、标签、来源、更新时间和旧版本一起保存。修改必须携带刚读到的版本号，过期修改会被拒绝，防止覆盖别人刚写的内容。团队草稿差异和真实私聊记录仍在工作台“管理员调试”中查看。

## 团队包声明

`manifest.json` 可增加以下字段，旧包不需要迁移。`knowledge/reader.md` 同时加入 `files`。

```json
{
  "knowledge": {
    "format": "wiki/1",
    "pages": [{
      "id": "reader",
      "title": "读者与写作约定",
      "summary": "目标读者、篇幅及标题规则",
      "path": "knowledge/reader.md",
      "tags": ["读者", "写作"],
      "sources": ["作者确认的编辑约定，2026-11-28"],
      "status": "confirmed",
      "links": []
    }]
  }
}
```

页面使用 Markdown，每页不超过32,000字符，每包最多200页。`links` 引用同包的页面 ID；目录不允许夹带未声明页面。`status` 为 `proposed`、`confirmed` 或 `superseded`；它只描述知识状态，不能替代 workflow 的人工确认。

新角色自动获得 `knowledge.lookup`，不必改 Skill 或 workflow。它只能读取项目锁定的团队知识、本项目知识及本项目协作记忆。正式工作模式下，具有写权限的角色还可用 `knowledge.remember` 保存待确认协作笔记；聊天、规划、走查和审核保持只读。

检索采用本地关键词与中文双字匹配，不依赖向量服务或额外付费 API。先返回相关短片段，再按页读取；长正文和旧版本均可分页读完。它不是语义搜索：未命中时需要换关键词，或查原始讨论，不能把未命中解释成“从未讨论”。

## 连续对话与用量

管理员续用同一 SDK 会话，服务重启后接续；检测到上轮上下文超过32,000 token 时，平台在下一轮前调用 SDK 原生整理，同一会话接续。先将可见用户与助手原文归档为可检索历史；不归档推理或工具大载荷。整理失败继续原会话，十分钟内不反复尝试。完整可见记录留在 journal，通过 `conversation_history` 检索并分段回读。Wiki 保存长期约定，对话会话负责“刚才那个”等临近指代；两者共同工作，不按轮次清空记忆。

输入、缓存读取、缓存写入、输出分别统计。SDK 续会话返回累计值时，平台减去上一次基线；旧会话缺少基线或上次中断时，明确显示“主调用统计”，不把整段会话累计量当作这一句话的消耗。这里只报告 token 数，不估算账单。

整理本身也消耗 token，计入该轮统计；记录整理前后的上下文大小，不把摘要节省比例当作账单节省比例。Wiki 不会自动把旧对话变小。节省来自按需取资料、复用缓存和避免反复读完整试跑轨迹，实际效果取决于问题和会话长度。

## 本地验证

以下离线检查不需要模型或飞书配置：

```bash
node --test test/knowledge.test.mjs test/admin-context.test.mjs test/admin-steward.test.mjs
```

只有选用文枢且希望补充真实 SDK 检查时，才运行下面的步骤；其他团队无需为此安装文枢。先完成标准 setup 的模型配置，再执行：

```bash
# 尚未安装文枢时下载固定上游版本；不创建额外机器人
node scripts/team-pack.mjs install newtype
# 会消耗模型额度；使用文枢隔离副本，不应用新版本
node scripts/verify-knowledge.mjs --live
```

真实 SDK 记录写入 `data/admin/knowledge-tests/<时间戳>/evidence.json`，明确标记为 SDK 测试。真实飞书私聊另外检查 `journal.jsonl` 中的 `feishu-private` 入站消息凭据；内部调用不能替代真人测试。

原生整理使用 SDK 的 `/compact` 命令，保持同一会话，未调用 `/clear`。参考：[官方 SDK 命令文档](https://code.claude.com/docs/en/agent-sdk/skills#compact-history-with-compact)。
