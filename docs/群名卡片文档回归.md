# 群名、卡片与文档回归

日期：2026-11-28。范围：本机服务、文枢 1.0.1 锁定包、真实 Agent SDK 与飞书接口。没有替换专业 Skill 或修改作者定义的 workflow。

## 可以怎样验收

在飞书打开本次「文枢 · 飞书交付验收」群，查看最新的「飞书交付验收 · 验收内容｜AI 主编」卡片：

1. 群名能看出团队与项目主题，不再是一整段指令。同名新项目自动加编号，创建重试不重复建群。
2. 「确认」是主操作，「打回修改」是警示操作；资料入口放在单独区域，带 `↗`，使用默认中性色。点资料入口不会批准项目。
3. 「最终交付」打开文章文档，标题为「产品即分发：转发按钮救不了没有价值的产品」。最新版本直接进入五段文章：问题、观点、标明是假设的例子、行动建议、边界。内部核查记录与文章分开。
4. 本次停在最终验收，用户可点「确认」进入原归档流程，或点「打回修改」并提出意见。历史版本采用追加保留，最新正文在文档末尾。

私人群和文档链接只在本机验收记录与交付对话中提供，不放入公共仓库。

## 实际运行证据

| 项目 | 结果与边界 |
| --- | --- |
| 创建项目 | 复用已有文枢机器人，通过现有创建接口新建独立项目群；从飞书群接口回读名称，与本地登记一致 |
| 首轮执行 | 副主编规划 → 作者起草 → 编辑 → 事实核查 → 主编汇总 → 等待最终验收；5 个角色均有成功 Skill 回执 |
| 打回修订 | 审稿发现成品被包成「交付汇总」，从原验收关口打回；再次规划、编辑、核查、汇总，回到最终验收；累计 9 次任务成功 |
| 正文 | 最终文件为一个文章主标题加五段正文；去除空白后 865 个字符（含标点），符合本次 600–900 字要求 |
| 飞书文档 | 初稿、编辑稿、核查记录、最终交付均真实创建并共享给项目群；从原生接口回读标题与正文，没有残留 Markdown 标题、加粗外壳 |
| 卡片 | 原生消息回读确认标题及按钮类型 primary / danger / default；文档按钮为「最终交付、编辑稿、核查记录」，带 `↗` |
| 再次同步 | 原文档继续追加版本，不新建重复文档；刷新文档和卡片不改变当前阶段或批准记录 |
| 本机测试 | `npm test`：290 项通过；`npm run smoke`：111 个文件语法检查、假飞书/模型工作台、首次启动引导通过 |

中间审核由 Coding Agent 根据用户授权进行回归点击，反馈明确写明「不代表真人已阅读」。最终验收未代点、内容未发布。模型引用的审批记录也区分了自动回归与真人验收。

## 回归发现与修复

- 动态计划开始执行后，卡片仍显示「选择协作方案」：改为当前可执行任务名称。
- 文档按钮用了角色职责长句：改为可识别的产物名称；其他专业产物保留包定义名称。
- 当前进度重复上一任务的「等待验收」回复：运行中的卡片只显示当前步骤，完成摘要留在结果或待审卡。
- 主编把文章包成「交付汇总」，摘要露出内部阶段标识：补强共用呈现提示，真实走原打回流程修订，未用程序重写文章论证。
- 本次新建的最终文档已经用了旧汇总标题：核对原生标题未被人工改动后，仅定向修正这一文档标题。没有批量改名、删除历史正文或覆盖人工评论；这不代表系统会自动重命名历史文档。

## 对抗审查

核对同名并发创建、请求重试、显式标题被错误剥词、Unicode 截断、旧卡失效、跳转按钮混带流程动作、运行中混用旧摘要、跨项目文档与评论隔离等路径。相关回归通过，未发现本轮变更造成的权限或阶段绕过。专业 PRD 的章节、FR/SC、代码、来源与本地 frontmatter 保留测试继续通过。

飞书接口回读证明实际消息与文档已落地；手机、桌面的最终视觉体验由用户在上述群中验收。这一轮真实运行针对内容团队，不把它表述为重新执行了全部团队、全部角色或联网事实研究。文章为委托观点及假设例子，未调用外部事实检索；格式通过不等于所有生成内容永远正确。
