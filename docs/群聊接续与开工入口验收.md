# 群聊接续与新项目入口修复

日期：2026-11-28。本轮针对“群里说话没反应、旧项目里聊了新目标却不开工”的实际问题，不修改团队包的 workflow。

## 根因

1. 主编已收到用户的新选题和补充，但旧项目已归档。原团队包聊天强制 `proposal.action=none`，协调机器人能说“我再排稿”，却不能提出新项目开工卡；此前显式入口也只匹配新研究，漏掉写作目标。
2. 主编最后一次回答等待约一分钟后失败；当时投研的三项任务占满全局三个执行名额，群聊排队超时，尚未启动该次 SDK。原回复未区分排队、模型回答失败和正式任务暂停。
3. 普通群消息只留档，每一条都必须再次 @；这与人在被追问后直接回答的习惯冲突。
4. 同一机器人的 open_id 在不同应用视角不同。真实消息接口证实用户的 @ 正确；第一次留档来自其他机器人时可能记为无目标，后续目标机器人仍能收到并回复。不能只凭首份留档的空 targetRoles 判断消息丢失，也不能用显示名称充当可信身份。

## 修复

- 协调角色在完成群中收到新研究、写作等目标，或根据补充对话提出 `start`，由代码核对角色、完成状态后发开工卡；点卡才新建独立项目，仍校验发起人，旧项目不重开、不自动确认。
- 聊天独立更新“已收到 → 正在排队 → 正在回复 → 回复/未完成”卡，不覆盖正式确认卡。群聊等待名额最多五分钟，轮到后模型回答最多一分钟，不提高全局三个名额的上限。
- 已失败的正式任务仍走原重试；没有正式任务失败时，“重试”仅重答该角色上次失败的消息。失败原因保留在项目诊断字段，不再把排队失败笼统称为模型没回答。
- 最近讨论直接进入聊天提示；不强制每次读取整份报告，也不等待逐份联网拉取文档评论。需要文档意见时读取后台已同步的本地评论。
- 同一真人单独 @ 一位角色后，十分钟内无 @ 的补充继续交给该角色。按项目和可信人员身份隔离；其他人、其他群、有真实 @ 的消息、多角色点名和过期接续不误派。“结束对话/暂停对话/不用回复了”关闭接续。原网页项目保持原行为。
- 当前完成状态优先于历史“待验收”说法；聊天回复卡附真实飞书文档按钮，文档路径不再充当阅读入口。清理公开摘要中的孤立 JSON 结束符。

## 验证

- 265 项测试通过，涵盖新写作入口、补充对话提议、非协调角色不能发起、原确认卡不被聊天改动、排队超时与主动停止区分、同人/跨群/跨人/过期接续、机器人消息去重，以及“好的”不推进确认关口。
- 真实主编群：使用已有“产品即分发”需求，主编约七秒完成回复并发出开工卡，保留 AI 爱好者、2000 字以内、联网核实三个约束。回测操作显式标记为 Coding Agent，不冒充新真人意见，未代点开工。
- 真实主理人群：先检查无其他真实任务，再短暂占用三个测试名额；确认出现排队卡后释放，随后同一卡片变为正在回复并得到真实模型回答。测试占位已清理，正式项目保持完成。
- 最后再次实测主理人状态问答：回复正确说明项目已完成、历史待验收按钮无需再操作，并附综合报告等三个真实飞书文档按钮。主编开工卡与主理人回复卡均通过飞书原生消息接口回读。三个既有项目保持 `done`，执行与排队名额均为零。
- 飞书真人无 @ 接续本轮验证了入站事件与身份路由回归，未伪造真人入站事件来声称线上人工验收。

实时回执和原始对比保存在本机 `本地资料/2026-11-28-群聊修复/`，不随包导出。已安装团队包内容、正式确认关口、角色与文件权限均保持不变。
