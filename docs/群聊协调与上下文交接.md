# 群聊协调与上下文交接

在已有飞书项目群里，无需每次 @：主编、研究主理人或产品经理会接收普通发言，识别问题应交给谁。未知群仍不自动建项，微信群尚未接入。

## 从一句话到一次交接

1. 接入层保存真人原话、发言人、附件元数据、引用消息 ID。多机器人重复推送只记录一次；机器人自己的发言不触发新的任务。
2. 只在本群查找被引用的消息，不跨群取原文。明确点名非协调角色时尊重该角色；其他情况结合引用对象、最近会话和当前阶段，由协调者选择已有角色。
3. 协调判断使用隔离、只读会话，只能选择包内角色，不能写文件、调用生产技能或推进工作流。分派后带上原话、发言人、引用和本项目最近讨论。
4. 问题交给相应角色回复。补充与修改生成单独确认卡；模糊意图先澄清。消息队列按群串行，不同项目可并发，但仍共享全局三个执行名额。多人发言分别保留身份，不把甲的表态算成乙的确认。
5. “好的”“收到”“谢谢”等普通应答不自动通过关口。“不用回复了”关闭该成员在该项目的自动接话，重新 @ 角色恢复；其他成员不受影响。明确“停下”“重试”等原有指令仍校验权限后处理。

如果旧机器人收不到未 @ 的群消息，需在飞书开发者后台给协调机器人开通 `im:message.group_msg` 并发布。新建基础版产品经理也会申请该权限。团队包的标准注册流程原本已申请全部群消息权限。

## 补充卡如何执行

卡片展示原发言人、原话、建议接收角色，以及「确认交给同事」「先只记录」。它和正式验收卡使用不同编号，不会覆盖正式确认卡。

- 确认权限沿用原项目规则：原关口指定确认人，其他阶段由负责人确认。普通成员可提出补充，不可替负责人批准修改。
- 目标角色仍在执行时，通过原 SDK 的 steer 接口传入确认后的补充。接口不再接收插话时，明确说明已保存、后续任务才会携带，不能声称本步已处理。
- 当前是可打回关口时，通过原 reject 入口重做，不直接跳阶段或另造任务。计划批次审核也使用已有打回规则。
- 暂时没有该角色任务时，把确认记录保存在本项目 `context/confirmed-inputs.json`；以后派给该角色时显式带入。它不启动未经原工作流授权的任务。
- 流程已推进或另一张补充卡已取代它时，旧卡失效。自动审核模式也不会把普通聊天直接当作新目标授权，补充确认与内容审核是不同事情。
- “先只记录”不生成执行指令，原话继续保留在完整讨论中。

所有角色仍读取各自项目的 Workspace，专业 Skill 和作者定义的依赖不变。附件目前仅记录引用元数据，不能假称已经读完图片、语音或文件。

## 实现与验证

| 内容 | 位置 | 验证重点 |
| --- | --- | --- |
| 入站原话、引用、附件、去重 | `src/projects/events.mjs` | 多机器人重复事件只交一次；显式多人点名分别处理 |
| 协调路由契约 | `src/packages/group-routing.mjs` | 限定角色和意图枚举；非法输出退回协调者澄清 |
| 标准包队列、分派、确认交接 | `src/packages/engine.mjs` | 可信身份、旧卡、阶段变化、负责人权限、原关口打回 |
| 原网页团队接话 | `src/projects/coordinator.mjs` | 调用原 handleMessage，复用提议卡和执行中引导卡 |
| SDK 路由模式 | `src/agents/run.mjs` | 只读、独立会话、有排队与回答时限，不续用作者会话 |
| 工作台确认入口 | `web/teams.js` | 展示原话，调用与飞书相同的授权入口 |

离线测试使用隔离身份与假模型验证边界。真实模型试跑在隔离本机项目执行：普通提问由协调者分给校对员回答；修改要求生成提议；“好的”没有改变阶段、正式卡号或任务数量。真实模型验证不冒充真实用户在飞书里的消息。此前已跑通的文档同步、卡片按钮和文档结构规范同时发布，见相应验收文档。
