# 完整应用团队：从规格到上线

## 目标与现状

新增一支「应用开发团队」，能交付有前端、后端、数据库、迁移与部署记录的可运行应用。原「筑页」单文件网页团队保留，旧项目继续锁定原团队包。

当前团队包可以编排角色、Skill、文件交付和人工关口，但 `web-studio` 的产物固定为 `site/index.html`；运行时只给 Agent 文件读写、Skill 和只读研究工具。现有 `files` 校验不执行测试、数据库迁移或应用健康检查。因此仅增补提示词和角色，不能宣称已具备完整应用开发能力。

## 角色与交接

| 角色 | 负责什么 | 主要交付 |
| --- | --- | --- |
| 产品经理（协调者） | 澄清目标、用户流程、验收标准，维护需求变更 | `spec.md`、验收场景 |
| 设计师 | 交互与视觉方案，明确页面状态 | 原型、设计说明 |
| 架构师 | 技术方案、数据模型、API 契约；实现后独立审查 | `plan.md`、数据模型、架构审查 |
| 程序员 | 前后端、数据库迁移、自动化测试、缺陷修复 | 可运行源码、迁移、测试 |
| 测试与部署工程师 | 启动隔离环境，验证端到端场景，执行受控部署并复测 | 测试报告、部署记录、线上冒烟 |

架构设计和架构审查由**同一个架构师角色在不同节点**完成。审查节点开独立只读会话，读取已确认方案与实际代码；后续如需更强独立性，再增加第二审查角色。程序员先作为全栈角色，避免尚未有任务依赖和执行器时就增加多个写同一目录的角色。

## 工作流

项目级原则和技术选型写入团队包的 `constitution.md`，作为版本化团队知识。每个项目按下面的顺序运行，Spec Kit 步骤与平台关口一一对应；不在群里直接执行任意 CLI 命令。

1. **澄清与 Specify**：产品经理写需求、用户故事和可验证的成功标准；人确认需求。
2. **Plan**：架构师写前端、后端、数据库、API、运行环境和迁移方案；设计师补齐交互。人确认技术方案与界面。
3. **Tasks**：把规格拆为有依赖的任务，标注角色、输入、输出与验收方式。平台检查任务图和写入范围。
4. **Implement**：程序员完成源码和测试；每个任务保留变更、运行结果与关联规格。
5. **Converge**：架构师只读核对规格、API、数据模型和实际实现；不通过时回到对应实现任务。
6. **Test**：测试角色在隔离环境执行迁移、单元/集成/E2E、应用启动和健康检查；失败附复现步骤回给程序员，修复后重跑。
7. **Deploy**：用户选择本地部署目标时发布到隔离的本机应用端口；有明确的服务器目标与凭据时才部署到远端。部署后真实 HTTP 冒烟，失败自动回滚到上一个可用版本，修复后重新发布。
8. **Accept**：展示运行地址、功能场景、数据持久化、测试与部署结果，由用户完成最终验收。

Spec Kit 的 `specify → plan → tasks → implement → converge` 是方法与产物模板；角色调度、确认、重试及版本锁继续由本项目的团队包引擎执行。Bug 修复走独立的「复现 → 修复 → 回归 → 重部署」回路，不重新生成整份需求。

## 平台需要补齐的能力

1. **应用交付契约**：团队包声明源码根目录、前后端入口、数据库类型、迁移、测试命令、启动命令、健康检查和运行端口。校验包时拒绝越界路径与未声明命令。当前 `artifacts` 只支持单文件，需增加应用产物类型及对应校验器。
2. **隔离执行器**：源码构建和脚本运行进入每项目独立容器，限定目录、网络、CPU、内存和时长；模型拿不到宿主机命令执行权。Docker 不可用时明确停在「待运行环境」，不能把文件存在当成测试通过。
3. **数据库生命周期**：本地默认 SQLite，项目各自独立数据库；迁移在测试库先执行，再在部署目标上执行并记录版本。需要多人写入或多实例时，可由方案节点选择 PostgreSQL，不把具体数据库写死在开放团队包协议里。
4. **部署目标与回滚**：先支持本机隔离预览；服务器部署须绑定目标主机和发布策略。保存部署版本、健康检查与回滚记录。AI 可以提出发布和修复，但真正发布按安装时选定的人工或自动审核模式执行。
5. **工作台与飞书**：展示规格、架构、任务图、测试证据、运行地址和版本；卡片区分「审核/执行」与「查看交付物」。失败给出具体复现步骤和负责角色，旧项目状态不受新团队影响。

## 实施顺序与验证门槛

| PR | 内容 | 最低完成条件 |
| --- | --- | --- |
| 1 | 应用产物协议、Spec Kit 模板映射、新团队角色与流程 | 包可校验、导出再导入；旧团队回归通过 |
| 2 | 容器执行器、测试与 SQLite 迁移 | 隔离项目可以构建并启动；故意失败的测试与迁移必须阻断流程 |
| 3 | 架构复核、缺陷回路、工作台/飞书呈现 | 从审查失败到修复复测可追溯；旧 workflow 不变 |
| 4 | 本机发布、健康检查、回滚；可选服务器适配 | 一个真实应用完成需求到本机验收；故障发布能回滚 |

发布前须用一个新建测试项目验证：提交表单经后端写入数据库，重启应用后数据仍在；无效输入返回清晰错误；架构审查、测试和部署日志可从项目档案追溯。既有机器人与项目不参与该试跑。

方法来源：[GitHub Spec Kit](https://github.com/github/spec-kit)（MIT）。采用其规格、计划、任务、实现与收敛方法；具体模板或 Skill 移植时记录固定上游版本及许可证。
