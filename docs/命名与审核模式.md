# 项目命名、卡片与阶段审核

适用于标准团队包引擎中的筑页、观澜、文枢以及导入的兼容团队包。原始启航版/领航版网页引擎继续保留四个人工关口；要采用自动审核的网页项目，请在团队工作台选择「筑页」团队包创建。

## 安装与创建项目

Coding Agent 首次搭建应询问：关键成果希望由人确认，还是交给独立自动审核？默认推荐人工确认。用户已明确选择时不要重复问。

```sh
node setup.mjs review human
# 或
node setup.mjs review auto
```

该命令写入 `.env` 的 `TEAM_REVIEW_MODE`，新建团队包项目读取它，不需要为改默认值重启。工作台创建表单可以逐项目覆盖；项目创建后固化方式，不中途改变审核权限。旧项目没有该字段时沿用原工作流，不追加关口。升级后的旧安装尚未选方式时，也保持原行为并提示选择。`.env.example` 为新安装提供 human 默认值。

| 方式 | 计划与批次 | 作者定义的关口 | 失败处理 |
| --- | --- | --- | --- |
| 人工确认 | 协作计划生成后先确认；同一依赖批次完成后审核，再派发下游；没有紧邻确认关口的独立任务也审核 | 原关口保留，不重复加相邻关口 | 指定确认人或项目负责人打回，提供修改意见 |
| 自动审核 | 独立只读 SDK 会话核对实际交付与需求，记录依据 | 非问答关口独立检查后继续；需要真人补信息的问答表单始终保留 | 未通过、缺少依据、文件变化或读取不全均停下；可重试审核、打回修改或结束 |

协作任务、角色、技能、依赖和文件契约仍来自锁定团队包。审核是平台执行层的暂停/检查机制，不修改作者包或自动安装新版本。自动模式的创建确认代表授权按这些规则执行，不意味着真人已阅读每份稿件，也不授权对外发布、买卖证券等外部操作。

审核会使用模型额度并计入全局并发名额。它结合已有确定性文件检查与模型的内容检查，不能保证事实完全正确。模型必须通过 Read 实际读取每个受检产物，返回逐项依据、结论和阻塞问题；不能仅用作者摘要作为通过证据。审核使用新的隔离会话，工具只有 Read/Glob，禁止写入、计算、检索和派活。

人工审核仍遵守项目成员与确认人权限。额外批次关口默认由项目负责人确认，作者定义关口使用原有确认人。卡片同时绑定项目、阶段、卡片号；待审文件内容发生变化，需要重新阅读并确认。打回只重做当前批次，已通过上游保留。重启保留待审位置；审核中重启按未完成处理，不自动通过。

审核结果保存在项目 `reviews`、工作区 `context/reviews.json`，在工作台「阶段审核记录」可见。正式关口的自动确认写入 approvals，来源为 `auto-review`、操作者为「自动审核」，不伪装真人。

## 群名与卡片

- 群名：`团队简称 · 项目主题`，例如「文枢 · 产品即分发」「观澜 · 中国神华现金流」。优先使用明确填写的名称，否则从明确选题/需求开头压缩；主题最多 24 字。清理“请你帮我研究一下”等连续指令前缀和读者/交付说明。开工卡提前显示建议群名；同名新项目加（2）、（3）区分，重试沿用登记名称。明确填写的标题按标题处理，不能再次剥掉“研究”等有意义的词。复杂需求可在创建表单指定准确名称，不保证规则自动理解长需求。
- 团队包卡片标题：`项目主题 · 当前事项｜角色`。普通问答带当前阶段和「讨论」，成果确认写具体关口。不会把角色职责说明直接当项目标题。
- 推进流程的主操作为蓝色；打回/结束为红色；纯跳转为默认中性色，统一带 `↗`，独立放在「查看资料」区。飞书卡片使用平台提供的 primary/danger/default 样式，不假设支持任意按钮颜色。
- 跳转按钮只有 URL，不能携带流程回调。资料入口不会改变项目状态。
- 旧群名、已经发出的历史卡片和已验收项目不会批量重写；新群与后续发出的卡片使用新规则。

测试：`node --test test/review-mode.test.mjs` 覆盖计划审核、批次审核、打回、重启恢复、旧卡、内容变化、自动失败与来源标记；`npm test` 运行累计离线回归。真实 SDK 与真实飞书测试结果另记，不能用替身通过冒充真实验收。
