# AI 团队包与开放生态：需求及规范草案

2026-11-27。本文保留实施前的需求讨论原稿，以下“尚未实现”等表述代表当时状态。当前实现以 [AI 团队包规范](AI团队包规范.md) 为准，验证范围见 [团队包验收](团队包验收.md)。本次实现已在本机运行，尚未发布到 GitHub。

## 目标与用户使用方式

作者分享的是自己设计、调试好的整套 AI 团队：角色提示词、Skill、协同工作流 Skill、Workspace 模板及其相互关系。使用者安装团队包后，在飞书项目群里提出项目目标，团队按作者的协同规范运行。

用户不需要理解技能调用命令。工作群是交互入口，项目是运行和上下文隔离单位。Agent 由角色提示词与 Skill 构成，统一使用平台提供的 Agent SDK；本轮不接入作者自带的独立 Agent 服务。

平台版本与团队包分开：启航版、领航版描述运行方式；网页开发、投资研究、文章创作描述团队能力。第三方增加团队包，无需新增平台版本，也无需改平台源码。

## 三套初始化团队

| 团队包 | 角色与分工 | 协同方式及交付 | 来源与状态 |
| --- | --- | --- | --- |
| 网页开发 | 产品经理、设计师、程序员 | 保留已验证的澄清、PRD、设计、开发、走查、验收及打回；交付单文件网页 | 从现有团队转成标准包；保留原角色与技能语义 |
| 投资研究 | 协调角色、信息雷达、收益与风险分析、投资判断、推荐、专业风投评审 | 明确研究目标；资料收集、不同观点分析、交叉评审、汇总证据与待确认事项；交付研究报告 | 新建示例包；上述角色名和任务边界是建议默认值，可由作者改配 |
| Newtype 内容团队 | 主编、副主编、研究、事实核查、资料提取、写作、编辑、归档 | 按目标选择所需角色，支持资料优先、研究核查、写作编辑、最终复核与归档 | 优先适配官方 newtype-codex 的方法层；保留来源与上游许可 |

三包必须通过同一个加载器、编排机制、会话隔离和权限机制运行，不能给每一包再写一套专用服务。角色数由包声明，不能固定为三个。使用同一个角色的多个项目可并行，但仍共用平台的总执行名额。

## Newtype 调研依据

已查到同一作者的三个仓库：

- [newtype-os](https://github.com/newtype-01/newtype-os)：仓库公开的是 OpenCode 插件版，README 明确完整 Workstation 和集成 CLI 的源码不在该仓库。
- [newtype-codex](https://github.com/newtype-01/newtype-codex)：一个主编编排 Skill、八个角色模板，最贴近本项目的“角色提示词＋Skill＋协同规范”。
- [newtype-lite](https://github.com/newtype-01/newtype-lite)：轻量方法包，不能当作八个真实 Agent 协作的替代证据。

本次核对 newtype-codex 的 HEAD：`e22b7771549572439a092295bb370075ded261a3`，插件清单版本 `0.2.2`。已读其 [编排 Skill](https://github.com/newtype-01/newtype-codex/blob/e22b7771549572439a092295bb370075ded261a3/plugins/newtype-codex/skills/newtype-chief/SKILL.md)、[协同规范](https://github.com/newtype-01/newtype-codex/blob/e22b7771549572439a092295bb370075ded261a3/plugins/newtype-codex/references/newtype-agent-workflow.md)和主编、副主编、写作角色模板。

适配时保留以下语义：主编负责用户沟通、调度和最终汇总；副主编提出计划和交接说明；专业角色完成自己的任务。资料充分时直接写作，已有草稿优先编辑，不能把所有请求都强制走同一条完整流水线。知识区与任务状态区分别保存，并纳入项目工作区。

Newtype 的 [插件清单](https://github.com/newtype-01/newtype-codex/blob/e22b7771549572439a092295bb370075ded261a3/plugins/newtype-codex/.codex-plugin/plugin.json)标记 `SUL-1.0`；上游 [LICENSE.md](https://github.com/newtype-01/newtype-os/blob/main/LICENSE.md)限制对外分发用途并要求保留许可和修改声明。适配方案采用**独立来源包与安装适配器**：记录固定来源版本，使用者安装时取得上游材料并保留许可，不将上游角色和 Skill 混入 MIT 核心代码或改标为 MIT。正式分发前还需核对该具体版本的许可材料是否齐全。

不执行上游的全局安装器，不修改使用者已有的 Codex/OpenCode 全局配置；把团队定义适配到本平台的项目实例。上游的宿主专用代理调度、搜索和资料读取工具，要映射成平台实际提供的能力。

## 包的标准组成

建议目录如下，文件名是本草案的约定，尚不代表当前程序已能读取：

```text
team-package/
  manifest.json             # 包名、版本、作者、许可、平台兼容范围、入口与依赖
  agents/                   # 各角色定义与提示词
  skills/<skill-id>/SKILL.md # 技能及其必要的脚本、参考资料、资源
  collaboration/
    SKILL.md                # 团队如何协作的说明与判断原则
    workflow.json           # 可执行的关系、步骤、分支、关口和交付约束
  workspace/                # 角色工作区、共享区、知识区、交付区的初始化模板
  examples/                 # 示例需求、示例输入与预期交付标准
  checks/                   # 可复现的验收用例
  LICENSE                   # 本包许可
  THIRD_PARTY_NOTICES.md     # 有第三方内容时提供
```

### 必填声明

| 部分 | 必须说明什么 |
| --- | --- |
| 包清单 | 唯一 ID、名称、版本、作者、用途、许可、标准版本、兼容的平台版本、成员文件和来源依赖 |
| 角色 | 唯一角色 ID、显示名、职责、提示词路径、可用 Skill、工具能力、读写与记忆范围、模型能力需求 |
| Skill | 唯一 ID、版本、说明、输入、输出、依赖资源、需要的工具；名称和引用必须能被解析 |
| 协同关系 | 入口角色、角色间可以分派/交接/复核/汇总的关系、协调权限、人工参与事项 |
| 调度规则 | 指定或可选技能、前置条件、依赖、顺序/并行/分支、完成条件、退回与重试边界、终止条件 |
| Workspace | 初始结构、角色私有区、共享资料区、知识区、交付区、允许读写范围、可带走的模板与经验 |
| 配置需求 | 外部工具、模型能力、待安装者填写的变量名与说明；不包含真实密钥或飞书账号身份 |
| 验收 | 可执行的示例任务、各角色预期产物、协作检查、缺失能力时的预期行为 |

工作流不只是一张 A→B→C 的表。编排需要同时支持两种协同形态：

1. **明确阶段**：网页团队的确认、设计、开发、走查等有固定转换。
2. **协调角色规划**：内容或研究团队根据请求提出受约束的执行计划，选择角色、技能和并行关系。

协同 Skill 描述专业判断；结构化规则限定可执行的关系、产物和权限。协调 Agent 给出的计划要先由编排验证，再执行；不能用自然语言绕过人工关口、越过读写范围或调用未声明的角色和工具。规划输出也要留档，便于恢复与复现。

## 安装、项目运行和更新

安装入口接受仓库链接、固定版本或本地团队包。安装器解析清单、校验完整性与依赖、列出所需模型/工具/飞书角色绑定，再获取缺少的配置。每个对外角色绑定相应的飞书机器人；已有的可复用，缺少的按标准安装流程创建和授权，不能只换名字冒充完整绑定。

创建项目时选择已安装的团队包。平台在本机保存项目锁定信息，包含包版本、依赖来源、内容摘要、角色绑定与配置引用；为项目初始化会话和 Workspace。真实凭据只保存在使用者本机。

用户在项目群里提出目标、补充材料和按规范确认。群内讨论与 Agent 发言按项目记录，专业角色的协作由编排管理，避免机器人消息互相触发循环。跨项目只复用声明的角色规范、技能和公共知识，不自动把项目原文放进共享记忆。

已运行项目固定团队包版本。更新团队包先用于新项目，已有项目是否迁移需要显式操作和兼容检查，不能在任务中途静默换提示词、工具或流程。

网页、文章和研究报告的文件类型不同，工作台的阶段、角色、关口和产物视图也必须由包提供的描述生成，不能继续写死为三个角色与 HTML 交付。启航版、领航版既有项目仍保留兼容入口。

## 作者打包 Skill：team-packager

这是给作者使用的制作工具，安装者继续在项目群里使用团队。建议请求形式：

> 把这个目录里已经调试好的 AI 团队整理成可分享的团队包，保留它的协同规则，并验证别人能在新项目里复现。

Skill 配合确定性的检查/导出程序完成：

1. **识别现有团队**：盘点角色、技能、协作关系、工作区约定、工具配置和实际交付。缺少的协同规则向作者核实，不仅凭一次聊天猜测。
2. **生成标准定义**：将原有团队映射到规范，保留原稿和映射说明；任何不能表达的行为列为缺口，不悄悄简化。
3. **明确导出范围**：只导出声明的提示词、技能、模板、示例和明确选择的公共经验。排除凭据、账号绑定、真人资料、项目聊天及 SDK 会话；历史项目数据仅在作者明确选择后另行处理。
4. **自动检查**：核验角色/Skill 引用、路径和依赖、协同关系、输入输出、关口与终止条件、许可文件及敏感数据。
5. **在干净项目复现**：从导出内容安装，验证所需文件和工具完整、步骤可运行、交接正确。结构检查、替身测试、真实模型、真实飞书分别记录，不能相互冒充。
6. **生成可分享产物**：输出团队包、文件摘要、固定依赖记录、安装说明和验证报告。发布到 GitHub 属于单独的作者指令，不因“打包”自动上传。

仅写一段打包提示词不算完成：目录收集、校验、导出和重新导入必须实际可执行。Skill 使用项目提供的同一套校验器，避免作者与安装者遵守两种标准。

## 完成标准

| 验收 | 必须证明的结果 |
| --- | --- |
| 三包通用 | 三套团队都经同一加载器和编排运行，角色与步骤不硬编码在各自服务中 |
| 自定义包 | 作者用打包 Skill 导出第四套小团队，在新目录安装后运行，无需改平台源码 |
| 协同保真 | Agent 关系、Agent/Skill 关系、角色权限与 Workspace 约定均与作者定义一致 |
| 工具完整 | 内容与研究所需的搜索、网页读取、资料提取等能力真实可用；没有来源时明确缺材料，不用生成文字冒充研究 |
| 项目隔离 | 两种不同团队的项目并行运行，群、会话、文件、确认人及状态互不混用 |
| 导出复现 | 导出后移除原作者目录依赖，安装者仍能通过示例验收；生成文字允许变化，机制与交付标准不变 |
| 兼容 | 已发布的启航版、领航版和现有两个完成项目不被迁移或改坏 |
| 边界真实 | 新机器人扫码、权限审批、工具缺失、多人真人联调等未完成项明确列出 |

## 本次讨论后的实施顺序

先冻结包规范与校验器；再把现有网页团队转成首个包；用 Newtype 适配包检验非线性协作；补齐投资研究包；最后用作者打包 Skill 导出并在干净环境安装第四套团队，检验开放生态确实成立。过程中发现标准表达不了的现有行为，先调整标准与对应测试，不改作者的协作意图。

本文件只记录已讨论需求、调研证据和拟定标准。当前没有声称三个团队包、导入器、通用编排或打包 Skill 已开发完成。
