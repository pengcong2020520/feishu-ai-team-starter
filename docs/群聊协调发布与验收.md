## 本次真实验证

在单独本机验收项目中，使用真实 Agent SDK 和已配置模型完成一次简报起草，再回放普通群消息：

- “校对员会从哪几个方面检查这份简报？只解释，不修改。”由协调者路由给 reviewer，后者实际回答。
- “请把这份简报的读者改成新入职同事。”被识别为 change，生成独立补充确认卡。
- “好的”没有触发另一轮模型，也没有批准正式关口。
- 回放前后正式阶段、正式卡号和已执行生产任务数量不变。

隔离回放使用明确标记的测试身份，只保存在忽略目录 `data/group-routing-acceptance/`，没有伪造真人事件到正式项目。真实飞书只发送 projectId=test 的展示卡，不改变现有文章与报告。本次没有重新完整运行全部内容和投研长流程。

## 对抗审查与修复

1. 新下载无法复现：投研包引用的 workspace/demo.md 被泛化忽略规则漏掉。改为只忽略根项目工作区，提交虚构演示模板，独立导出目录重新测试通过。
2. 多角色点名被误去重：分派回执按消息与显式角色组合去重，同一条点名多人仍分别处理，普通群消息只进入一次协调判断。
3. 普通聊天越权：只读路由没有写入或生产工具；变更只生成提议。补充卡重新校验负责人，拒绝普通成员代批准；自动内容审核也不绕过此变更确认。
4. 任务已结束却报告插话成功：只有 steer 返回成功才称已交给当前任务；否则记录确认输入并明确告知后续处理。已交付成果走原 reject，不另造跳转。
5. 引用串群与身份混淆：引用只匹配当前群 recorder；发言人与确认人分别记录。只有可信入站的活跃身份进入群聊协调；机器人发言不触发循环。
6. 路由期间阶段变化：检测阶段/任务历史摘要变化后，退回协调者澄清。旧补充卡同时校验阶段与历史摘要，不能对新阶段生效。
7. 模型无效路由：不接受不存在的角色或动作；退回协调者澄清，不执行模型输出的任意指令。
8. 修改转交执行尚未成功：补充确认转交原关口后，再报告已开始修改；原关口拒绝时明确回复未执行。

边界：微信群未接入；附件只保留元数据；模型路由仍可能判断不准确，可明确 @ 角色纠正。原网页团队的队列由原编排处理，标准包的回执有持久化去重。已接收但服务中断的路由不会自动伪装成功，重发消息可重新处理。真实飞书测试为接口接受与消息读回，没有声称完成多客户端像素审查。
