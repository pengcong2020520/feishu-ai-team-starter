# 选择部署位置与保持服务运行

飞书是交互入口，Agent SDK 和项目代码运行在用户选择的机器上。初始化先确定机器，再配置模型、扫码和启动；同一组机器人只能由一台机器连接。

## 初始化分流

Coding Agent 必须先问「部署到服务器，还是本地电脑？」已有明确选择就沿用。

- 本地：执行 `node setup.mjs deploy local`，再执行 `node setup.mjs`。依赖、模型、机器人就绪后，setup 安装系统常驻服务，再启动它。
- 服务器：收集 SSH 主机、用户名、端口、登录方式和部署目录。私钥留在用户机器，只提供路径；密码不写入项目配置。执行下列命令记录远端交接信息，随后在实际运行机器继续安装。本机不会继续扫码或启动同一组机器人。

```sh
node setup.mjs deploy server --host example.org --user ubuntu --port 22 --path /opt/feishu-team --identity-file /本机/密钥路径
```

不用指定密钥时省略 `--identity-file`，沿用 SSH Agent 或 SSH 配置。真实参数须替换，含空格的路径正确引用。不要关闭 SSH 主机指纹验证。部署记录只存于忽略提交的 `data/deployment.json`。

## 本地常驻

| 系统 | 实现 | 自动启动范围 |
| --- | --- | --- |
| macOS | 当前用户的 LaunchAgent，RunAtLoad + KeepAlive | 登录该用户后自动启动；不弹终端。退出登录后不运行，不声称是登录前的系统守护 |
| Linux | 当前用户的 systemd 服务，Restart=always | 安装后启用；还须 `loginctl enable-linger` 才能在开机后无人登录时运行 |
| Windows | 本轮没有原生常驻安装器 | 请使用受支持的 Linux 服务器；不能把临时后台启动当作自启动已安装 |

macOS 的 plist 放在用户 `Library/LaunchAgents`，Linux unit 放在用户 `.config/systemd/user`。名字包含项目绝对目录摘要，使用 Node 和入口的绝对路径。只写工作目录、PATH、日志路径等信息，不把模型或飞书密钥复制进系统配置。移动目录或更换 Node 安装位置后，先卸载旧任务再重新安装。

```sh
npm run status                  # 当前进程、自启动范围
npm stop                        # 停止系统任务，守护不会立即把它拉回
npm start                       # 再次通过系统任务启动
node setup.mjs service uninstall # 停止并移除自启；保留项目与配置
```

`npm stop` 不删除安装文件；下次登录或开机仍可按系统规则启动。要长期停用用 uninstall。重新运行 setup 会按已选择的部署位置重新安装。Linux 必须用实际运行账号检查 `loginctl show-user "$USER" -p Linger`；尚未启用时 setup 明确提示未完成，不报告全部就绪。权限不足时由系统管理员授权。

常驻不等于永远在线：关机、休眠、断网和模型服务故障仍会影响运行。需要全天在线应使用持续开机且联网的服务器。不能自动修改用户的系统睡眠设置，不能把 macOS 登录自启称为开机登录前运行。[Apple 的用户 Agent 说明](https://developer.apple.com/library/archive/documentation/MacOSX/Conceptual/BPSystemStartup/Chapters/CreatingLaunchdJobs.html)、[systemd 用户 linger](https://www.freedesktop.org/software/systemd/man/latest/loginctl.html)。

## 在服务器安装

1. Coding Agent 用用户提供的 SSH 信息检查目标系统、Node.js 24、Git、网络和目录权限。在专用普通账号下运行，确认 systemd 用户会话可用。无可用用户服务的环境可使用仓库原有 Docker 方案，不把两套守护同时装在同一组机器人上。
2. 在目标目录保留完整 Git 仓库，使用用户选定的版本或提交；不能在部署时无意退回尚不包含当前功能的 main。按标准 setup 流程填写模型密钥、安装依赖。
3. 在远端代码目录执行 `node setup.mjs deploy server --here`，再执行 `node setup.mjs`。先启用当前运行账号的 linger；缺少权限时请管理员处理。这些步骤由 Coding Agent 在远端执行，不要求用户手工重写服务文件。
4. 首次扫码仍执行标准 `node setup.mjs scan`。服务器临时开启仅监听 127.0.0.1 的二维码页面并打印端口。Coding Agent 在用户电脑用 SSH 转发该端口，打开打印的地址，由用户手机扫码；确认完成后临时服务关闭。不通过公网暴露二维码或仓库目录。
5. 最后核对所有已绑定团队、管理员连接、工作台和预览服务；服务重启后项目和待确认卡保留。用 SSH 隧道访问实际端口，Node 安装默认如下：

```sh
ssh -N -L 4870:127.0.0.1:4870 -L 4871:127.0.0.1:4871 ubuntu@example.org
```

工作台和预览仍只监听回环地址，不为扫码或看板开放公网端口。端口被 setup 自动调整时，隧道也必须同步调整。

已有 Docker 部署继续使用 `compose.yaml` 的 `restart: unless-stopped`，并启用 Docker 自身开机启动；宿主端口仍是 4880/4881，容器内 4870/4871。容器中设置 `TEAM_SERVICE_MANAGED=1` 让内部团队进程意外退出后恢复。Docker 与用户 systemd 二选一，不额外启动第二份 Node 服务。[Docker 重启策略](https://docs.docker.com/engine/containers/start-containers-automatically/)。

## 项目如何接续

两层守护分工如下：系统拉起管理服务；管理服务在团队子进程意外退出后按 5 秒起、最高 60 秒的退避间隔重新启动。显式停止不会被当成崩溃。原飞书 SDK 长连接负责网络重连。

新选择部署位置时记录 `recovery: resume-interrupted`。服务连接飞书后，只接续启动时被识别为「上次正在执行、未主动停下」的任务，复用原工作区和原调度路径；团队包保留已经完成的计划任务。待恢复标记持久化，首次启动因网络不可用失败后，下次启动仍能识别原中断任务。十分钟内同一项目最多自动接续一次，再次中断时留待人工重试，避免无限消耗模型额度。

人工确认、验收、未开工提议、主动停止/结束、业务校验失败和模型额度错误不因服务恢复而自动批准或重试。自动恢复在群内标明「服务恢复」，不伪装用户点击。旧安装在未选择部署位置前维持原有手工恢复行为。

若从本机迁移：先等任务结束，停止并卸载旧机器自启，确认连接已关闭，再迁移完整代码、`.env`、项目 `data`、`workspace` 和会话数据。不要传 `node_modules`、活进程 PID、锁、并发槽、原机的 service-manager/deployment 配置或二维码缓存。目标机重新选择部署位置；目录变化时需验证 SDK 会话路径，不能只保留会话号就宣称续用成功。此轮没有远端迁移实测。

## 本轮验收

- 本机 305 项累计测试和启动冒烟检查通过，验证安装先选位置、服务器不在本机扫码、路径引用和配置无密钥、停止不反弹、进程异常重启、项目接续和确认关口保留。
- 当前 Mac 已实际安装 LaunchAgent，plist 通过 `plutil -lint`；分别终止团队子进程和管理进程，真实服务均重新启动，已有项目阶段、确认卡号与错误状态保持不变；主动停止不会被立即拉回，再次启动正常。本机证据在 `data/deployment-fault-check.json`，不提交私人数据。
- 对抗审查补上恢复通知期间用户结束项目的状态复核、启动失败后恢复意图保留，以及迁移前停用本机守护、远端选择后禁止本机 resume/增补扫码的检查。
- 未重启用户电脑，不能把进程故障测试称为整机重启实测；Linux 的实际开机、远端部署、Docker 宿主重启和 Windows 原生服务均未在本机验证。
