# 管理员团队调试实测

日期：2026-11-28。本机使用已安装的文枢 1.0.1，复制为“个人产品观察”，不修改原团队包与已有项目。

## 实际执行

| 环节 | 结果 |
|---|---|
| 私聊处理链 | 自然语言调用管理员 SDK 工具，复制团队并修改草稿 |
| Agent | 修改主编、作者的产品观察定位，保留八角色 |
| Skill | 补充作者技能的假设案例标注与正文要求 |
| Workflow | 保留原节点图；在个人草稿中要求八项协作任务，并补充读取模板的任务说明 |
| Workspace | 添加栏目编辑约定模板；实际运行记录确认作者读取了该文件 |
| 真实试跑 | 八角色、八种 Skill 均有成功回执；完成十项任务，生成八份产物 |
| 故障接续 | 首次检查超时后，从主编失败节点继续；前面已完成步骤没有重做 |
| 成品 | 文章《先有可展示的成果，再谈分享》通过独立检查，正文与归档文件分开保存 |
| 应用 | 安装个人团队 1.0.0，新项目可选择；已有项目保持原版本 |
| 导出与导入 | 35 个文件真实上传至飞书私聊；从飞书下载后，经文件消息处理器导入另一草稿。除新团队标识、名称等清单信息外，文件逐一一致 |
| 隔离 | 原项目状态文件及原来八份已安装包版本的摘要保持一致；导入草稿没有自动安装 |

这里的“真实”指实际模型、Skill 回执、飞书卡片和文件 API。私聊入站由标明自动联调的测试适配器送入同一个处理器，没有伪称真人发消息；试跑中的确认关口标为 `automated-test`。角色协作运行在独立本机项目，不借用正式项目群。新增个人团队需要通过标准扫码流程连接自己的机器人。

成品检查保留了两处非阻塞文字建议：来源行有内部确认说明，个别表达可更明确。这次验证的是团队定制与调试链路，不代表任意内容都无需编辑即可公开发布。

## 发现并修正的问题

- 测试入口退出会带停试跑：改为独立后台进程，服务停止时仍能找到并停止此前启动的调试任务。
- 成品检查的三分钟限制在本次模型调用中超时：采用任务允许的时限，最多十分钟，保留实际错误；检查规则没有放宽。
- 失败试跑缺少中间成果：失败和停止也收集可读取产物，支持原节点接续。
- 运行记录可能被通知回写覆盖：通知独立保存；失联状态只在读取时判定，存活进程不会因睡眠后的心跳延迟被重复启动。
- 应用锁在异常退出后遗留：应用与提示词编辑共用带进程标识的锁，并回收已退出持有者。
- 跨进程编辑与应用可能竞争：草稿操作共用跨进程锁；锁的持有者信息完整写好后原子发布，避免无持有者的短暂空隙。
- 样例预期不能替代正式交付要求：两者取并集；没有实际角色执行、替身测试、过期草稿均不能用于应用。
- 已应用草稿不能原地变更：继续定制时从正式最新版本创建下一版草稿。

Grok CLI 独立审查提出了运行记录、锁恢复、交付要求等问题，以上修复均补充了针对性测试。模拟关口是隔离试跑的明确设计，正式应用仍需管理员的明确指令或卡片点击；不把试跑称为真人审阅。

复审中的样例清单意见按协议区分处理：每个 `examples` 是独立测试目标，不把另一案例的可选交付物强加给当前需求；匹配样例时追加其预期文件，当前 workflow 的最终交付要求始终检查。启动回执的写入失败也不会把已启动子进程误标为失败；运行记录中的进程号为实际依据。

## 复查方式

本次全仓测试 364 项通过；冒烟检查覆盖 146 个模块的语法、工作台启动和首次安装入口。成功与失败两种调试卡片均通过真实飞书接口发送，测试按钮不会执行正式动作。

```bash
npm test
npm run smoke
```

私聊操作示例见[管理员助手](管理员助手.md)。本机原始记录保存在 `data/admin/team-lab/acceptance/record.json`，逐次试跑和成果在 `data/admin/team-lab/runs/`；这些运行记录与项目内容不提交到仓库。

## 真实私聊补测与工作台记录

同日追加测试使用飞书客户端中已登录的管理员账号，实际向「AI 管理员助手」发送消息。官方消息查询返回发送者类型 `user`，发送人、会话和正文均与长连接入站记录匹配。没有调用 `onMessage` 或注入消息事件启动这轮测试。

测试复制文枢为独立草稿「私聊调试 · 产品观察」，通过私聊完成主编与作者提示词、作者 Skill、任务调度要求和编辑指南模板的修改。首条输入遇到中文丢失，随后在同一私聊补发完整要求；补充进入正在执行的管理员轮次，两条实际消息均保留。

发现并通过私聊修正了一个调试偏差：管理员先把“必须覆盖八项任务”写成保留目录、仍可选择子集。测试停止第一轮，保留记录，再明确修改必做任务约束。第二轮实际执行八个角色、八种 Skill、十项任务，产出八份文件；作者调用了新增工作区指南。试跑检查通过，关口仍标明 `automated-test`，不是人工审阅。

第二轮最终稿附带内部“验收状态”和来源编号。独立检查识别到了，却判为非阻塞，没有触发修正。随后用户从真实飞书私聊提出修正，管理员修改主编角色及 `chief-method` 中冲突的要求，并启动第三轮试跑；没有通过内部调用代替这条消息。

第三轮完成八角色、八种 Skill、十项任务和八份产物。最终稿《导出的完成清单，发出去就收不回来》约七百汉字，保留假设声明和公开来源；实际读取全文后确认不再包含验收尾注、sourceId、内部路径或待确认说明。独立检查完成，保留两条非阻塞编辑建议供用户查看；模拟关口只验证编排，最终内容是否合用仍由用户验收，草稿未应用。旧稿和问题记录均保留，未覆盖成新的成功记录。

用户还在真实私聊强调最终验收由本人决定。这条指令及管理员答复保留在“全部调试”的最近对话里（没有草稿操作，不强行关联修改）。界面与后续通知使用“技术检查完成”，不把自动回归称为用户已验收。本机凭据核对覆盖五条真实用户消息，发送者、会话与正文均与飞书官方查询一致。

工作台增加“管理员调试”入口，显示原始指令、实际回复、消息凭据、逐次修改前后全文与差异、关联试跑及成果。历史内部调用明确标记；不补造缺失对话。旧试跑保留其固定草稿版本，后续修改不会覆盖差异记录。

对抗审查采用 Grok CLI 并逐项复核，修正了读写两侧脱敏规则不一致、列表和详情对话归属不一致、无轮次的内部操作被遗漏等问题。排队轮次不与上一任务合并；插话保留关联；SDK 工具内发出的文件回复继续归属原指令。离线测试 371 项通过，冒烟检查通过。网页检查覆盖导航、真实私聊详情、逐行差异及前后全文展开。

本机证据在 `data/admin/team-lab/acceptance-private/`，完整对话在 `data/admin/journal.jsonl`。原项目工作区、状态与已安装包共 1,385 个文件的内容摘要一致，正式项目没有被修改。以上目录均不提交 GitHub。
