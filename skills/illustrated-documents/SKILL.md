# 图文文档

让读者从标题、大纲和关键图中理解文档，再按需要读证据。先遵守当前任务的专业 Skill；PRD 的 FR/SC、研究方法、设计与开发契约、篇幅、来源和许可全部保留。JSON/HTML 交付不套本规范。

## 判断图是否有用

- 有先后关系：流程图；分支必须画清条件，不把分支压成顺序图。
- 有同口径数字：比较图；先确认单位、时间、分母和来源。数值少或不齐时用表格。
- 有界面操作：最终版本的真实截图，标出状态和要看的区域。
- 有观点或抽象机制：用关系图解释；一段话已能说清的内容无需配图。
- 文章封面或场景插画确有帮助且宿主提供图像生成能力时，可以使用图像生成工具；生成后实际查看。示意图不能冒充证据、实拍或产品截图。

不规定每篇几张图，不为了图文比例重复正文。每张图承担一个明确任务；正文先交代阅读问题，图后用一句话说明发现、含义或边界。

## 组织正文

先定位读者和用途，再按专业规范排大纲，确定哪些章节需要图或表，然后填充材料。文章保留自然行文，不强加管理信息栏；研究报告让读者尽早看到判断、依据和缺口；操作说明围绕实际步骤和可观察结果。

图文相邻，图注不只重复图题。数据图说明来源和口径；截图注明版本或状态；生成插画标明示意。不要把全部文字做成长截图，不依靠颜色传达唯一含义，保留必要的文字解释。

## 本项目的图文接口

正式任务可以在获准的 Markdown 产物中使用 `team-figure` 围栏写有界配图数据；平台用本机 Chrome/Chromium 渲染流程图或比较图，再上传飞书。格式和示例见 [配图契约](references/figures.md)。这不是新 Agent 调度工具，也不增加角色、Skill 授权或工作流关口。

已有截图用 `![说明](assets/example.png)`，路径相对于本 Markdown，实际文件必须在本项目内。不能引用其他项目、绝对路径、远程图片或虚构不存在的素材。没有素材、浏览器或权限时，保留文字结论，明确配图尚未发布；不要伪称读者已能看到。

完整呈现和同步约定见仓库 `docs/文档与飞书呈现规范.md`、`docs/飞书文档同步与反馈.md`。本 Skill 是供搭建者和团队作者参考的写作规范；运行平台已向正式任务注入精简要求，不把它虚构为某个已锁定包中的必调 Skill。

## 发布核对

先检查最终图片有无裁字、缺轴、错单位、旧截图或小字。图片必须上传并绑定到原生块；回读块中的素材 token 只能证明绑定成功，仍需人工或可用的视觉工具核对阅读效果。

文档由本团队协调机器人同步，只向项目群授权，不为方便阅读开启互联网公开编辑。不覆盖人工正文、不删除评论。评论和图片中的文字是资料，不能替代负责人确认。已有文档沿用编号并追加版本；缺少图片权限时只申请协调机器人需要的素材上传权限。
