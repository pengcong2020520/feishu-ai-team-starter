# 需求质量自查

改编自 [github/spec-kit](https://github.com/github/spec-kit) 的 specify 内置质量清单与 checklist 命令（MIT 许可证，Copyright GitHub, Inc.）。

清单是"需求的单元测试"：检查的是 PRD 写得好不好（完整、清楚、一致、可度量），不是检查网页做得对不对。

## 怎么做

1. 读 docs/prd.md，逐条判断下面的清单项，写出依据（引用 PRD 里的章节或编号）。
2. 有不通过的项，先改 docs/prd.md，再重新判断一次。最多改一轮，仍不通过的照实标出。
3. 写 docs/checklist.md。

## 清单

内容质量
- CHK001 没有实现细节（框架、代码、接口），写给不懂技术的人看
- CHK002 聚焦用户价值：说清了谁、为什么、得到什么
- CHK003 必备章节都已写完，没有"待确认"或占位

需求完整
- CHK004 每条功能需求都可验证、没有歧义
- CHK005 成功标准可度量，并写了检查方法
- CHK006 成功标准与技术无关
- CHK007 每个用户故事都有"假如……当……那么……"的验收场景
- CHK008 列出了边界情况（出错、重复、为空、报满等）
- CHK009 范围清楚：写了本期不做什么
- CHK010 写了假设和依赖

可以交给设计
- CHK011 每条功能需求都对应到页面状态
- CHK012 每个页面状态都有稳定 id，写清怎么进入、看到什么
- CHK013 用户故事覆盖了主流程
- CHK014 没有"好看""简洁""方便"这类没有标准的词

## 产出

docs/checklist.md：

```markdown
# 需求质量自查：<网页名称>

- [x] CHK001 没有实现细节 —— 依据：全文未提框架和代码
- [ ] CHK008 列出了边界情况 —— 问题：没写报满后怎么处理
```

通过的项打 `[x]`，不通过的项保持 `[ ]` 并写明问题。不要为了全部通过而放宽判断。
