# 需求澄清

改编自 learn-codex-harness 的 agent-brief（资料卡与深度引导），以及 [github/spec-kit](https://github.com/github/spec-kit) 的 clarify 命令（MIT 许可证，Copyright GitHub, Inc.）。

## 第一步：扫描哪里不清楚

逐项看下面的分类，在心里标"清楚 / 部分清楚 / 缺失"，不用写出来：

| 分类 | 要弄清什么 |
|---|---|
| 定位与范围 | 网页叫什么、给谁用、要完成哪件事、明确不做什么 |
| 页面内容 | 一定要展示的信息、真实文案从哪来 |
| 交互与流程 | 用户的操作顺序；出错、为空、加载、成功时分别看到什么 |
| 数据 | 要收集或展示哪些字段、怎么算重复、有没有数量上限 |
| 边界与失败 | 重复提交、输入错误、报满、刷新页面等情况怎么处理 |
| 风格与参考 | 想要的感觉、参考的页面 |
| 完成标准 | 怎样算做成了，能不能靠看页面、点页面来检查 |
| 含糊的词 | "好看""简洁""方便"这类没有具体标准的说法 |

## 第二步：挑问题

- 只问答案会改变页面内容、流程或验收的问题；用户已经说清的、纯技术实现的、无关紧要的风格偏好都不问。
- 按"影响大小 × 不确定程度"排序，先问影响最大的分类，不要在一个分类上问两个小问题。
- 每轮最多 3 个问题，在飞书里一屏能看完。每题给 2–4 个互斥的选项，标出推荐项和一句理由；推荐依据是同类页面的常见做法、风险更小、与用户已说的目标一致。
- 问题要是一个完整的问句，不懂行的人只看问句也能回答；不要拿"字段范围"这类标签当问题。
- 选项和推荐项都要是具体、可以直接用的内容（例如"线下，本周六 14:00–16:00，市图书馆二楼"），不要推荐"先用占位文案、以后再替换"——用户点"全部按推荐"后，页面就该用这些内容。
- 一个问题只问一件事，不要把"形式""时间地点"揉在一题里。
- 和 PRD 合计最多 3 轮。用户说"按推荐""直接写"，或者已经是最后一轮时，不再提问，直接用 prd-spec 技能写 PRD。
- 用户说"以后再说"的内容，写进 PRD 的"本期不做"或"假设"，不当作已承诺的功能。

## 提问时的产出

提问这一轮不写 PRD，只写 docs/questions.json（每轮覆盖）：

```json
{
  "round": 1,
  "why": "一句话：为什么要问",
  "questions": [
    {
      "id": "q1",
      "question": "报名时需要填写哪些信息？",
      "matters": "一句大白话：这个答案影响什么",
      "options": ["姓名和手机号", "姓名、手机号和单位", "姓名、手机号和想读的书"],
      "recommended": 0,
      "reason": "信息越少，报名越快"
    }
  ]
}
```

`recommended` 是推荐选项的序号（从 0 开始）。系统会把这个文件做成飞书卡片：每题列出选项、标出推荐项，并附一个"全部按推荐"按钮。

## 回答怎么用

写 PRD 时，在"产品概述"之后加一节"澄清记录"，逐条写 `问：…… → 答：……`（用户说"按推荐"的，写推荐项）。每条答案同时落到 PRD 对应的章节：功能需求、用户故事、边界情况、成功标准或假设；被答案推翻的旧说法直接替换，不留前后矛盾。

最后的回复：一句话说明为什么要问，不超过 40 字。
