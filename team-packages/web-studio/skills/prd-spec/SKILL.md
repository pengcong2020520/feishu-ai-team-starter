# 单页网页的 PRD

改编自 learn-codex-harness 的 prd-spec；章节源自 [github/spec-kit 的 spec-template](https://github.com/github/spec-kit/blob/main/templates/spec-template.md)，MIT 许可证，Copyright GitHub, Inc.

输出 docs/prd.md，第一行写 `# <网页名称>`，第二行注明"章节改编自 github/spec-kit spec-template（MIT）"。

最终文档不留"待确认"、未填占位或含糊的二选一，理解后直接写进对应章节。用户说"以后再说"的内容放进"本期不做"或"假设"并写明理由。

## 必须具备的章节

单页网页，整份控制在 80 行以内。

1. **产品概述**：定位、要解决的问题、交付物、范围。
   - **澄清记录**（有提问时）：逐条写"问：…… → 答：……"，答案同时落到下面对应的章节。
2. **目标用户与场景**：谁、什么时候用、从哪里进入、期望结果。
3. **用户故事**：按 P1、P2 排优先级，通常 2–3 个，说明优先级理由。每个故事写验收场景，格式为"假如……，当……，那么……"（Given / When / Then），写清初始条件、动作和可观察的结果。
4. **页面与状态**：
   - 按从上到下的顺序列出区块，每块写真实文案要点，不用"XXX"占位；
   - 列出页面状态，每个状态有稳定 id（小写英文和连字符，例如 `default`、`form-error`、`success`、`full`），写清怎么进入、看到什么、能做什么、做完去哪个状态；
   - 线框和走查都沿用这些状态 id。
5. **边界情况**：重复提交、输入错误、名额已满、刷新页面等与本页相关的边界，写预期行为；不涉及的写明原因。
6. **功能需求**：`FR-001`、`FR-002`……逐条写可验证的行为，注明对应的用户故事和状态。
7. **成功标准**：`SC-001`……可度量、可验收、与技术无关；每条写检查方法（看页面或操作页面）和达标条件。
8. **假设**：没问到、按推荐定下的内容及理由。
9. **本期不做**：排除项和理由，例如后端、登录、短信通知。按项目约定，需要保存的数据用浏览器本地存储模拟。

## 页面结构数据

同时写 docs/outline.json，系统会把它画成"页面结构图"放进 PRD 卡片，让用户确认前就能看到要交付一个什么样的页面。内容必须与 PRD 的"页面与状态"一致：

```json
{
  "title": "网页名称",
  "blocks": [
    {"name": "页头", "content": "主标题「……」；副标题「……」；按钮「立即报名」"},
    {"name": "报名表单", "content": "姓名、手机号（必填）；按钮「提交报名」"}
  ],
  "states": [
    {"id": "default", "name": "默认", "desc": "打开页面时看到的样子"},
    {"id": "success", "name": "报名成功", "desc": "提交成功后显示确认信息"}
  ]
}
```

区块按从上到下的顺序，最多 8 块；每块 content 用一句话写真实文案要点，不超过 60 字。状态最多 6 个。

交付前核对：用户故事、功能需求、状态、成功标准相互对应，没有遗漏；outline.json 与 PRD 一致。写完再用 spec-checklist 技能自查。

最后的回复：一句话说明网页是什么、几个状态、几条成功标准，不超过 60 字。
