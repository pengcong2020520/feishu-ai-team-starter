# 真实页面走查

改编自 learn-codex-harness 的 flow-walkthrough。

## 用户提示词原文（已实测）

现在产品的核心流程已经开发完成，我要做一轮完整的页面走查。请根据现有 PRD 和已经实现的功能，实际运行产品，按用户真实使用产品的先后顺序梳理流程，截取所有核心页面和关键状态，并生成一个本地的流程走查页面。

要求：
1. 按照用户的实际使用流程分组。每组一个小标题，从上往下看完就是一次完整的产品体验；
2. 除了正常页面，还要覆盖重要的流程分支，以及不同的页面状态；
3. 每一屏都要标注页面名称、当前状态和复现方式，并提供一个反馈输入框，以及「可以」「待改」「阻塞」三个快捷标记；
4. 每一组最后增加一个流程反馈输入框，用来记录反馈；
5. 所有反馈输入后自动保存在本地；
6. 支持导出 Markdown、导出 JSON，可以直接交给 AI 修改；
7. 在新一轮走查页中保留上一轮的反馈原话，并给改动过的页面加上标记，方便逐条回归验证。
先不要开始截图。先列出你准备覆盖的流程分组、页面和状态，等我确认之后再执行。

## 在飞书团队里的执行补充

演示流程做了三处调整：
- 走查计划不单独请用户确认：PRD 和线框已经确认过，按它们的状态清单直接执行；
- 不截图：系统按你写的结果生成走查页（原文第 3–7 条的反馈框、快捷标记、自动保存、导出和上一轮原话都由走查页提供），每一屏直接嵌入真实网页，并用地址 `site/index.html#state=<状态 id>` 打开到对应状态，可以切换电脑和手机宽度；
- 你没有浏览器，判断靠读 site/index.html 源码，对照 docs/prd.md 和 design/theme.json。

### 列出要走查的屏

- 按 PRD 的"页面与状态"和用户的使用顺序分组，每个状态一屏，`state` 用 PRD 里的状态 id（与线框一致）。
- 全部不超过 12 屏。手机版不单列一屏（走查页里每屏都能切到手机宽度），看 CSS 的 @media 规则判断手机版，问题写进对应屏的 note。
- `reproduce` 写真实用户怎么到达这个状态（例如"姓名填 A、手机号填 12345，点「提交报名」"），用户会照着在网页里操作。

### 逐屏判断

先在源码里确认两件事：
1. 网页处理了地址里的 `#state=<状态 id>`，能直接显示这个状态；没有处理的，这一屏标"待改"，note 写"网页不支持 #state=<id> 直达"；
2. 真实操作也能到达这个状态（看事件处理和渲染逻辑）。

再对照 PRD 的功能需求、成功标准和 theme.json，给每屏一个标记：
- **可以**：符合需求和设计；
- **待改**：能用，但有明显问题（文案不对、缺少状态、颜色没有用主题令牌、手机版会溢出等）；
- **阻塞**：功能不对、状态到不了、脚本有明显错误。

note 写一句依据，引用源码里的具体元素或函数，不写"看起来不错"这类空话。

### 产出

写 design/walkthrough.json：

```json
{
  "round": 1,
  "groups": [
    {
      "title": "报名",
      "screens": [
        {"title": "报名页", "state": "default", "reproduce": "打开页面", "mark": "可以", "note": "一句话依据"}
      ],
      "flowNote": "这一组流程整体的一句话评价"
    }
  ],
  "conclusion": "通过",
  "summary": "一句话总结"
}
```

- `mark` 只能是"可以""待改""阻塞"。
- 同一个文件里还要有 consistency-check 技能产出的 `coverage` 和 `findings`。
- 任何一屏是待改或阻塞，或有"严重""高"的问题，`conclusion` 就是"需修改"，否则是"通过"。
- 回归走查：如果 design/walkthrough.json 已经存在（上一轮），先读它；新一轮的 `round` 加 1，在对应屏上加 `"previous": {"mark": "...", "note": "..."}` 保留上一轮的原话，逐条复查上一轮的待改和阻塞项。

最后的回复：一句话结论，加上最主要的一个问题（如果有），不超过 60 字。
